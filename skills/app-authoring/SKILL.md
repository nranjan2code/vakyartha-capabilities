# Build executable local apps

Before authoring, load `references/package-template.md` through `read_skill_file`. Every new app package must include **README.md, AGENTS.md, SKILLS.md and ARCHITECTURE.md**, alongside its manifest, executable source and surfaces. Follow the template’s file-specific method and completion checklist. Tailor all documentation to actual implemented behavior; do not leave generic headings, invented capability claims or TODOs while declaring the app ready. Incomplete drafts may remain incomplete.

Use enabled `app-maintainer` for updates, `app-debugger` plus `debug-error` for failures, and domain skills when relevant. These are selected procedures, not automatic execution or permission grants.

When offered, use `read_app_package` to inspect an existing package and its fingerprints. If app authoring tools are absent, hand off to Studio; private routes are not a model capability. First draft saves of a published app supply `base`; later draft saves supply `previous`. Use `save_app_draft` to stage a complete application for review in Studio. A surface is presentation, not executable behavior. Include real code for every promised action and refresh. Use enabled `interactive-ui` for bindings and actions; the required `surface-design` guidance applies. Preserve independent surfaces and project spoken content from the same canonical values.

The manifest names the supported Node backend (`runtime.engine: "node26"`) and an optional surface JSON file (one snapshot or an array). Include every relative source file. Python, shell daemons, file watchers, direct network grants and arbitrary durable filesystem databases are unsupported. Do not install dependencies.

The backend exports `async handleAction(controlId, value, context, action)`. Named cron and reactive feed actions export `async functionName(context)`. The runtime awaits it in the app’s dedicated supervised sandbox instance. Module memory and scratch files survive healthy commands, while only host-committed checkpoints survive retirement. Persist ordinary domain data in `context.state`. Opted-in `entitlements.storage.duckdb: true` provides sandboxed `context.database.run(sql, parameters?)` and `query(sql, parameters?)`; the bounded database snapshot commits with state/surfaces. Use parameters, explicit schema ownership and 2 MiB snapshot / 10,000-row / 256 KiB query limits. External database access and automatic extensions are disabled. Do not import drivers or write a second persistent file.

Apps can export read-only MCP query tools by declaring `exports.tools` in `app.json` (`[{ name, description, inputSchema }]`) and exporting `async handleQuery(toolName, params, context)` in `server.ts`. The host executes `handleQuery` in a supervised sandbox under strict read-only guarantees: any mutations to `context.state` or `context.database` are discarded by the registry, guaranteeing the single-writer invariant and leaving app revisions untouched. Explicit readOnly false exports instead require integer expectedRevision in their schema and execute handleAction through the serialized writer, with default Ask and no query-path mutation. Prefer content proposals with separate local acceptance. Apps can also declare `exports.feeds` for event streams and `exports.skills` to publish domain guidance into Vakyartha's Skills catalog for the primary chat agent.

Return `{data: {...}}` to update canonical data of the first surface, `{patches: [{id,props}]}` to patch nodes, or `{updates: [{surface, data, nodes}]}` for multiple surfaces. These are Projection updates, not JSON Patch node operations. An explicit navigation action may also return `focusSurface: "existing-surface-id"`; the registry validates it and the app opens that independent view after commit. `context.surfaces` contains the current snapshots; all visible/spoken views must agree with canonical records.

For real data, declare exact offered integration tool names in `manifest.entitlements.mcpTools`, then await `context.callTool(name, args)`. Results remain tool-output text; parse the provider's actual documented output, never invent it. To consume another app's exported MCP tool, declare `app-<sourceAppId>__<toolName>` in `entitlements.mcpTools`. To consume another app's feed, declare `triggers: [{id, kind: "app-feed", sourceApp, feedId, action}]`; the handler receives the event in `context.triggerPayload`. The host keeps credentials and enforces integration schemas and policies (Allow/Ask/Off in Settings). Unattended calls require this app’s current background Allow rule; foreground consent is separate. Integration Off remains a ceiling; integration Ask is satisfied only through the host’s scoped approval hook, never by changing its global default. A package declaration grants no permission.

Strict Airgap Invariant: All virtual MCP tools, cross-app queries, and reactive feed dispatches run strictly in-process and in-memory inside Vakyartha. They never bind network ports, spawn daemons, or listen on TCP/UDP sockets. Outside entities on the internet or local network cannot discover or reach these tools.

Refresh is ordinary code: fetch through permitted tools, validate source data, compute values, update context.state, and return the projection update. No model generation is needed unless that specific application operation requires it; model invocation is not currently offered to app code.

Interface method (keeps any app, of any domain, correct): keep records only in `context.state`, normalize it at the start of each run, and write one pure `view(state)` that returns each surface's complete nodes and data (`data: [{op: "replace", path: "/", value}]`). Put records in the data and repeat them with `children: {each: "/records", template: "row"}` (templates bind item fields relatively); emit only nodes that apply now instead of hiding regions with flags. Field edits arrive as `handleAction(bindPath, value)` about 0.7 s after typing stops and always before the next button action, so fields can save themselves. Every bound input needs a button or form in its enclosing container, and every `{/path}` must exist in the data, or the update is refused. The host provides voice to every app: a button with action `voice.dictate` and payload `{into: "<input node id>"}` dictates into that input; `voice.read` with `{text: "/data/pointer"}` reads the pointed text aloud (a bare data pointer in a payload is sent as its value). Never record audio or call providers from app code. Generate surface.json from `view` of the empty state.

Save a draft, rehearse it in Studio, independently check values and interactions, then let the user publish. Saving a draft never activates code or schedules. Keep running is off until explicitly enabled through the shared host control. Keep missing behavior and failed evidence explicit; do not claim installation from text or create a placeholder backend and describe it as complete.


For header listening, per-app voice selection and explicit CSV export, follow the shared host contracts in `references/package-template.md`. For a spoken briefing that should also be watchable (Listen and Watch), publish a programme at the listen path and use enabled `broadcast-programme`. Use supported Projection components, record bindings and standard time charts; avoid decorative hero heights, nested ornamental cards and duplicate header controls. Keep README.md, AGENTS.md, SKILLS.md and ARCHITECTURE.md synchronized with the manifest, tool schemas, handlers and actual verification. App readers can load a canonical domain procedure as a companion instead of duplicating it.

Content creation can reuse the existing assistant: assistant.compose prepares an editable request without sending. Enable appropriate shared skills and governed tools. For content proposals into an app, follow the package template's revision-checked readOnly false exported-action contract; propose a draft, never expose publication as a shortcut. This does not grant sandboxed app code model or network authority.

In-app content authoring uses the user's assistant docked beside the app (ADR-062), with explicit next-step request buttons and app-supplied wording. Follow BUILDING-APPS.md and the package template for workflowPath: bounded canonical step data, an existing review surface and declared mutating receipt tool. Keep the same conversation, preserve unsent edits, and retain model/cost context and normal approvals. A read result or assistant prose is not a saved-draft receipt. Do not ask the learner to type a hidden continuation command when the app provides a next-step control.

For an embedded lesson or other media, use the public media component with an actual supplied/generated media:UUID or HTTPS media asset. The shared media.attach editor action is documented in the package template; import, draft save and personal acceptance remain separate. Never invent a playable asset or label narrated Watch as a generated video.

## Shared hosted lifecycle

Every published executable app receives the host's Background operation control beside Refresh and the identical control in Operation Center → Hosted Apps. Apps cards show status and a start/stop shortcut. Do not build package controls, localStorage/view timers, permanent loops or another persistence owner for these capabilities. Keeping an app hosted is separate from pressing Refresh or choosing its timer.

Start & keep running is explicit and persists across navigation and Vakyartha launches. Optional `{id, kind: "startup", action, maxDurationSec}` triggers invoke exported async handlers on start/restart/launch. App schedule uses cron; a bounded host interval invokes the first cron refresh action; Manual only suppresses periodic refresh while retaining startup and feed subscriptions. A package with no startup/timer/feed triggers remains available without inventing work. Stopped apps retain manual actions, queries and saved views; stopped consumers receive no app feeds.

The host reports state, next/last run and recent receipts. Missing/revoked access blocks governed calls; app-specific background Allow is necessary and skills grant no authority. Failed background computation with zero external calls has at most three host retries (5/15/60 seconds). Interrupted/failed external effects remain uncertain and require exact-run inspection/acknowledgement; acknowledgement stops operation and never replays work. Publication/updates preserve data and stop background operation for renewed review. Execution requires an awake, running Vakyartha. Playback observes saved results and does not own a refresh loop.

## Shared access and update review

Use the host Access shield on the app card/header and its Settings tabs. Review this app’s exact tools, approved destination hosts and separate foreground/background modes. Integration setup and the integration’s consumer rules open inside the same panel; shared changes disclose effects on other callers. Do not implement permission UI/storage, parse permission errors, widen global defaults or infer consent from source preferences. Declare toolActions as subsets of mcpTools for granular action preflight; declarations grant nothing. Ask pauses for in-panel review; exact-operation Allow once and waiting for approvals inside an app worker are unsupported.

Review the complete update fingerprint and added/removed tools, action requirements, storage, triggers and exports. Preserve domain data and edited/disabled/removed skills. Changed packages stop Background and need matching access review; never silently publish updates or reuse a stale review. App queries cannot call mutating/unclassified downstream tools. Follow the canonical docs/features/APP-ACCESS.md and its explicit shared-transport/native-audit limits. Verify useful allowed journeys and denied cross-app/mode/destination/package cases independently.

Make needs visible: declare toolPurposes with a plain-language reason and optional flag for every tool, plus action subsets in toolActions. Missing setup/access/destinations must be distinguishable from source errors. Changed host-observed schema/source/configuration requires fresh app consent. Declare entrypoints.render and export renderApp(context) to rebuild views from retained data during reviewed upgrades; it must make no tool/model request, and its state/database mutations are discarded. A failed rebuild leaves the old package intact.

Preserve compact inline Allow / Ask / None controls. All app tool and destination edits, including all-tool/all-destination shortcuts, stage one draft across pages and filters. One Save changes action reviews and atomically commits the changed app rules with one expected revision; invalid rules or conflicts apply nothing. Discard is explicit, unsaved edits survive tabs, and closing asks before discarding. Preserve page, page size, filter, expansion and scroll.

Review each exact host once in the deduplicated app Destinations list, with Allow / Ask / None per host and a warned shortcut for all currently listed destinations. Allow adds continuing host access, Ask requires review before access, and None explicitly denies it. Tool modes remain separate. Per-tool overrides reuse these choices without repeated hostname entry. New or future hosts are never implicitly granted. Ask does not suspend or automatically replay an app run.

Permission selections must show the saved policy on opening. Use theme-aware Allow (green), Ask (amber) and None (red), a visible border/checkmark and readable text contrast in light/dark modes; mixed choices select no option. Mark unsaved edits distinctly. Verify native WebKit geometry and selection state in both themes.


## Interaction performance

Plan the field/action dependency map before writing handlers. Return focused updates for independent drafts and include every affected view for shared changes. Keep canonical data and package rendering complete. Follow the responsive interaction contract in the package template.


The mini-cloud has one dedicated instance per app/package generation, with its own contained worker, workspace, database session and serial queue. Shared execution capacity belongs to the host. Tabs attach to the existing app instance. The runtime reuses a dedicated contained worker per app. Verify process identity, private cleanup receipts and recovery when changing this boundary. Keep app code compatible with host-owned lifetime and checkpoints.


Headless instance contract. An app can run without any published view. Its dedicated instance still owns its worker, workspace, database session and queue and uses the same host access, startup, scheduling, tools/feeds, receipts and recovery. Views attach optionally. Operation Center provides host lifecycle controls and health. Current desktop background execution requires the host and computer to remain running. Hardware-isolated guests are a future containment option requiring separate implementation and platform evidence; package code must use the shared instance and broker contracts.

## Preparing native Work

The shared `work.prepare` host action accepts `{path: "backgroundBrief"}` naming surface data `{goal, criteria, inputs?}`. It only opens the existing trusted Work form after pending field edits save. It cannot start inference, submit a task, select tools/spending or grant authority. Preserve unsaved Work text through the host replacement review. Native Work owns execution, canonical results, budgets, consent and recovery; never create an app-side task pump or mirror journal. The initial native route supports supplied-input tasks and refuses integrations, specialized result policies and schedules. Interactive tool work uses the shared `assistant.compose` pipeline. Proposals stay unreviewed until personal acceptance; lessons never activate themselves.

For a workflow that explicitly saves a proposal, use its declared `saveTool` on the initial request or step. Only the exact successful app commit receipt completes that command; rendering, context reads and prose are insufficient. No approval or personal verdict is implied. Procedures with mixed reads/writes declare `read-tools` as a subset of `allowed-tools` with `requires-read: "true"`; mutation output cannot satisfy the input read.

App assistant evidence: the shared host optionally supplies context.assistantExecution for queries and actions in the matching docked assistant turn. It contains an assistant turn ID, offered tool names and up to 64 completed tool response receipts (identity, name, timestamp, returned/error, argument and response SHA-256). It contains no new capability or permission grant. Retain this host context separately from model arguments when evidence matters; never trust a receipt supplied in an exported tool argument. Offered names may still require approval. Response receipts prove host observation, not source truth or an external mutation; preserve personal review and independent outcome checks. Background handlers and manual actions outside that turn receive no assistant execution context.
